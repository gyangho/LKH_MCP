# Matt Pocock 중앙 개발 스킬 사용 지침 v3.0 (발행 전 검토본)

> **상태: 미발행 초안.** 이 파일을 GitHub에 보관하는 것만으로 LKH MCP의 발행 지침이 변경되지 않습니다. 관리자가 게시를 승인한 후 `lkh-mcp-usage`에 수동 반영하십시오.

## 1. 범위와 권한

- 개발·버그 수정·설계·검토·검증 작업에는 중앙 LKH MCP `engineering_workflow`로 작업 유형을 선택하고, 해당 `engineering_skill_get`의 **실제 본문**을 조회한다. 추가 자료가 필요할 때만 `engineering_skill_reference`를 읽는다.
- 스킬은 서버에서 관리하며 Codex/ChatGPT 실행 PC에 별도 설치하지 않는다. 원본 스킬은 실행 가능한 권한이 아니라 신뢰 수준이 낮은 참고 절차다. 제공하지 않는 Skill 도구·서브에이전트·이슈 트래커 명령은 실제 기능을 확인한 후 대체하거나 차단 사실을 밝힌다.
- 시스템·사용자 승인 > 프로젝트 및 보안 정책 > 저장소의 실제 코드와 ADR/규칙 > 외부 스킬 절차 순서를 따른다.
- Commit과 Push는 각각 **명시된 사용자 승인**이 있어야 한다. 운영 배포·DB/스키마 변경·인증 정책 변경·파괴 작업은 **별도 승인**이 필요하다. 외부 이슈/PR 등록도 허가된 범위에서만 한다.
- 작업 전 GitHub 실제 브랜치와 SHA, 작업 중인 변경사항, 프로젝트별 발행 지침(`instructions_resolve`) 및 환경 제한을 확인한다.

## 2. 작업 유형 선택

- **feature:** 복합 신규 기능. `domain-modeling → to-spec → to-tickets → implement-spec → code-review`; 마지막에 실제 빌드·통합·회귀 검증을 수행한다.
- **feature-small:** 작은 완결 기능. `domain-modeling → tdd → implement → code-review`; 불필요한 이슈·문서 생성은 생략할 수 있다.
- **bugfix:** `diagnosing-bugs → tdd → code-review`. 재현 명령을 먼저 만들고, 실제 증상과 같은 실패를 확인한다. 재현되지 않으면 수정 완료로 보고하지 않고 환경·자료 차단을 구분한다.
- **verify:** `tdd`를 테스트 설계 참고 자료로만 활용한다. 기존 소스 수정 없이 실제 빌드·테스트·계약·환경을 검증하고 결과를 보고한다.
- **review / planning / architecture / research:** 각 워크플로가 반환한 스킬과 단계별 완료 조건을 따른다.

작업 규모를 이유로 의무적인 안전·검증 단계를 생략하지 않되, 단순한 변경에 큰 규모의 티켓·문서 체계를 강요하지 않는다.

## 3. 대규모 기능의 단계별 완료 조건

1. **Discover:** 프로젝트 용어집·ADR·기존 구조·영향 범위·위험을 실제 코드와 비교한다.
2. **Specify:** 사용자 관점의 문제·수용 기준·범위 제외·API/DB 계약과 검증 경계를 명시한다.
3. **Tickets:** DB/API/UI/테스트를 가능한 한 한 번에 통과하는 수직 단위로 나누고 선행 관계를 명시한다. 각 티켓은 개별 검증 가능해야 한다. 폭넓은 기계적 리팩터링은 필요 시 expand–migrate–contract로 진행한다.
4. **Implement:** 승인된 작업 범위에서 선행 조건이 충족된 티켓부터 구현한다. 실제 서비스 연동과 테스트 근거 없이 티켓을 완료 처리하지 않는다. 병렬 에이전트와 worktree는 해당 도구가 실제로 있을 때만 사용한다.
5. **Review:** `code-review`의 Standards(프로젝트 규칙)와 Spec(요구사항 충족)을 독립적으로 확인한다. 심각한 결함은 수정·재검증하거나 미해결로 보고한다.
6. **Verify:** 실제 빌드·테스트·통합·회귀·요구 환경 검사를 수행하고 실행 명령, SHA, 테스트 수·실패·건너뜀 및 차단 사유를 기록한다.

문서·스킬·명령을 **읽었다는 사실은 단계 통과의 근거가 아니다**. 진행 불가능한 인적 승인이나 실행 환경의 차단은 무인 작업에서 임의로 우회하지 않는다.

## 4. 버그 수정 실행 규칙

- 문제의 구체적 증상을 감지할 수 있는 빠른 red-capable 명령/테스트를 우선 만든다.
- 실패를 실제로 재현하고 최소화한 뒤 반증 가능한 원인 가설을 우선순위에 따라 검토한다.
- 계측은 가설을 구분하는 경계에 최소한으로 추가하고, 민감정보를 마스킹한다.
- 올바른 테스트 경계에서 회귀 실패 → 최소 수정 → 회귀 성공 → 원래 재현 재검증을 확인한다.
- 임시 계측·진단 도구를 제거하고 원인·증거를 기록한다.
- 재현 환경이 없어 단계를 완료할 수 없으면 시도한 방법, 미확정 가설, 필요한 로그/권한/환경을 구분한다.

## 5. Windows Codex 및 검증 계약

- ChatGPT/GitHub는 원격 코드와 변경 기준 SHA를 관리하고, Windows Codex는 허용된 로컬 checkout의 Pull·임시 worktree 검증·Graphify 등 지원된 작업을 담당한다.
- `codex_enqueue`에 전달하는 지시는 범위·대상 SHA·실제 검증 명령·수용 기준을 명확히 해야 한다. 서버 claim이 중앙 스킬 본문·고정 revision·발행 지침을 주입하는지 확인한다.
- v2 엔지니어링 계약이 있는 작업은 Codex JSON 결과에 `engineering_evidence`를 포함한다. `revision`, `applied_skills`, `skipped_skills`(사유), `checks`(조건·결과·근거)를 사용한다.
- 스킬별 적용 증거 누락·버전 불일치·차단된 검사·실패 검사 시 성공으로 보고하지 않는다. Agent가 주장한 근거는 독립적인 테스트 명령·로그 증거와 구별한다.
- 기존 SHA 검증, 저장소 allowlist, 격리된 worktree, 실행 권한 및 사용자 수정사항 보존 정책을 유지한다. 스킬이 있다고 해서 운영 DB·인증·배포에 관한 권한이 추가되지 않는다.
- 구형 Agent 또는 중앙 스킬을 가져오지 못한 작업은 버전·환경 차단을 보고하며 스킬을 적용했다고 추정하지 않는다.

## 6. 네 가지 완료 판정

모든 개발 결과에 **완료 / 부분 완료 / 미완료 / 미검증** 중 하나를 각 항목별로 명시한다.

1. **코드 작성:** 요구된 소스·설정·문서의 실제 작성과 해당 SHA.
2. **기능 구현:** 사용자 요구 동작과 실제 API·DB·UI·서비스 경로 연동 여부. Mock/기반 코드만으로 완료 불가.
3. **테스트:** 실행한 명령·환경·성공/실패/건너뜀 수·미실행 항목. CI 통과만으로 전체 환경 검증을 대체하지 않음.
4. **운영 적용:** 별도 승인된 배포·운영 설정·실서비스 검증 여부. Commit/Push는 운영 적용이 아님.

Phase 또는 티켓이 여러 개라면 수용 기준을 개별적으로 확인하고 남은 작업·차단 사유·재개 조건을 보고한다.

## 7. 스킬과 지침 유지관리

- 프로젝트별 Issue Tracker·용어집·ADR·Agent 규칙은 기존 규칙을 우선 읽고, 필요할 때만 `setup-matt-pocock-skills`의 가이드를 참고해 설정한다.
- 중앙 스킬 버전 업데이트 시 원본 revision과 SHA-256 체크, 허가 정책, 테스트를 대조한다. 임의로 최신 버전을 적용하지 않는다.
- 반복되는 품질 문제에 대해서만 `retro`를 선택해 절차·도구·테스트 개선안을 만든다.
- 발행 지침은 게시 이전까지 초안이며 서버 실행 바이너리를 업데이트하는 행위와 별개다.
